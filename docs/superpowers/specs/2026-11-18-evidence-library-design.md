# WcCAT 长期资料库与多来源搜索存储设计

日期：2026-11-18（Asia/Shanghai）

状态：用户已于 2026-11-18 确认设计并授权实施，采用 SQLite 增量扩展。原数据库迁移与历史回填仍与代码交付分开执行。

## 目标与边界

把每次热榜、网页搜索、内容和互动观测保存为可追溯的证据，支持以后重算算法、追踪事件进展、交叉验证报道，以及在数据使用权限允许时提供查询服务。

本次建设存储基础、采集接入点、历史回填和可恢复备份。保持现有首页、日报和评分行为。未来周期性 AI 新闻线索分析、公开收费 API、支付、向量数据库和大规模评论采集不在本次实现范围。事件与 AI 证据关联的基础结构在本次预留并提供写入/查询接口，但不自动把标题相似判定为同一事件，也不自动认定因果关系。

用户选择继续使用 SQLite；每月数据与 DeepSeek 总预算不超过 30 元。初期免费接口优先。本次新增供应商默认禁用，只有后续取得 Key、验证免费权限并显式运行时才可请求；不自动注册付费方案、充值或开启自动续费。既有直连热榜、DailyHotApi fallback、正文抓取、worker 与 DeepSeek 调用保留原行为；本条不为既有无 Key 接口增设凭证要求。

本次不新增付费网络调用、不新增 AI 调度或分析次数，也不建设跨既有日报、翻译和分享链路的全局费用硬限制。30 元是运营预算边界，不宣称已由代码保证。新增搜索供应商本次交付存储与规范化契约，实际网络 adapter 在账户开通后接入；启用前需单独验证额度和设置费用上限。

## 已确认的现状

- `snapshots`、`raw_items`、`topics` 围绕小时标识保存，同小时重跑会替换原有业务记录。
- `raw_items` 实际是归一化后的条目，不保留完整上游响应；许多字段已经在适配时丢失。
- `topic_id` 由标题生成，不能直接充当长期稳定的事件 ID。
- 当前归档格式 v1 只识别六张业务表，校验器拒绝未知表；不能直接向归档加入新表。
- 清理小时快照会级联删除原条目、话题和分析；长期证据不能依赖这种外键关系。
- 本地库约 667 MiB，208 份快照；快照和话题表分别约占 291 MiB、284 MiB。长期存储应避免继续把正文和完整响应复制到每个话题。

## 方案比较与决定

1. 只向现有快照增加字段：成本低，但同小时覆盖、标题事件 ID 和重复大 JSON 问题仍存在。
2. 在同一个 SQLite 文件中增加独立证据表：保留旧链路，同时建立追加观测、内容版本和来源追溯。用户已选择此方案。
3. 立即迁移 PostgreSQL 与对象存储：现在引入额外运维、迁移和费用；以后可以通过仓储接口与版本化导出迁移。

新增表不加入旧的 `BUSINESS_TABLES` 集合。旧归档继续遵守 v1 的六表约定；新增完整数据库备份命令，覆盖新旧全部表。界面和文档明确区分“旧业务范围归档”和“包含长期资料库的完整备份”，避免误以为原来的 full 模式包含新证据。

## 存储原则

- 每个采集尝试有独立 run ID；同小时重跑不覆盖已记录的证据。
- 原始响应、规范化文档、文档版本、指标观测和搜索命中各自保存，互相用 ID 关联。
- 区分平台和供应商。例如通过 Apify 获取微博：platform=weibo，provider=apify，adapter 指向具体实现。
- 区分 published_at、source_updated_at、observed_at、recorded_at。未知时间为空，不用采集时间冒充事件发生时间。
- 缺失值使用 null，零值保留。指标附带名称、单位、统计对象与原字段路径。
- 对同一响应或正文做内容寻址与压缩去重；相同内容仍保留多次观测和不同供应商的发现关系。
- 证据不因清理旧小时榜被删除；不启用自动清理长期证据。
- 接口 Key、Cookie、Authorization、短信、账户密码不进入证据库、公开日志或导出。保留字段完整性不包括这些认证材料。
- 保存供应商返回数据不等于获得转售许可；来源条款、可保存范围和可再分发状态单独记录，未知状态不自动对外提供全文或评论。

## 数据结构

以下为逻辑字段；实现者可调整 SQL 类型、命名和索引细节，但必须满足唯一性、引用完整性和验收要求。ID 使用独立 UUID；内容校验使用 SHA-256。

### 1. library_sources

记录 provider、platform、adapter、能力类别（hotlist/search/detail/comments）、接口版本、使用条款 URL、条款核对时间、保存与再分发状态。唯一键为 provider/platform/adapter。

权限状态至少区分 unknown、allowed、restricted；状态必须有备注或来源链接。当前仅供内部研究使用，外部查询需要显式批准可分发的字段。

### 2. library_blobs

保存脱敏后内容的 hash、编码、压缩数据、原始字节数、压缩字节数、内容类型、首次保存时间。正文和 JSON 使用同一内容仓储。hash 覆盖编码与字节以避免不同类型混淆。限制单次响应体积，超限记录 truncated 标识和原长度；不得把截断结果当作完整原文。

### 3. collection_runs

保存 source ID、开始/结束时间、状态（running/success/empty/partial/failed）、脱敏请求信息、HTTP 与业务状态、原始响应 blob 引用、错误摘要、adapter/normalizer 版本、响应完整性、供应商缓存或更新时间、归一化条数与实际费用字段（可空）。

通用请求信息只保留白名单字段；API key 查询参数和所有认证请求头必须剔除。响应解析失败也保留脱敏响应和失败记录。

### 4. library_documents

保存稳定的文档 ID、platform、对象类型（article/post/video/question/answer/comment/topic_landing）、平台对象 ID（字符串，可空）、规范化 URL、首次/最近观测时间。

优先按平台对象 ID 匹配；缺少时按 platform + 规范化 URL。规范化去片段和明确的跟踪参数，但不去除内容识别参数；不跨域或跨平台擅自合并文档。同文转载保留各自文档，通过关系表关联。后续识别出对象 ID 时建立别名，避免复制已存在文档。

### 5. document_revisions

保存 document ID、规范化内容 hash、标题、摘要、正文 blob、published_at、source_updated_at、语言、父文档 ID（评论所属帖子等）、可选去标识化作者 ID、内容来源级别、首次观测 run ID。

相同规范化内容不新增版本；标题或正文变化新增版本，旧版本保留。正文和摘要保持分开。规范化 hash 不包含互动计数，避免每次点赞变化生成正文版本。供应商片段不可伪装为全文。

### 6. document_observations

保存 run ID、document/revision ID、observed_at、原始条目 blob 引用、源榜名次、热度原值与单位、字段完整性、数据对象范围、legacy_snapshot_date 与 legacy_row 标识（均可空）。

来源快照标识仅作追溯字符串，无指向旧快照的删除级联。相同 run 下相同文档的重复条目不重复写指标，但保留原始响应与出现位置，能够诊断重复页。跨 run 观测继续追加。

### 7. metric_observations

保存 observation ID、metric、numeric_value（可空）、raw_value、unit、scope、raw_field_path、状态（observed/missing/unsupported/invalid）。

区分评论总数、根评论数、回复数，避免互为别名时相加；保留播放、点赞、收藏、分享、赞同、反对、弹幕等原含义。只在明确声明单位时换算。大 ID 与超过安全范围的原始数字以字符串保留；不静默损失精度。

### 8. search_queries / search_runs / search_hits

search_queries：规范化查询、原查询、查询用途、版本、语言、地区、时间过滤、站点过滤与排序参数。配置的等价查询共享逻辑 ID，但每个引擎的实际改写仍在 run 中保存。

search_runs：query ID、collection run ID、engine/provider、实际查询、请求页/游标、分页是否结束、返回数量、观测时间、缓存状态。分页错误不能标记完整结果。

search_hits：search run ID、页内名次与全局名次、结果类型、目标 document ID、该次命中的标题/片段、引擎声称的发布时间（附来源和不确定性）、原始结果 blob。

同一文章被两个搜索引擎找到，文档可复用，但两次搜索命中都保留；同一文章多次搜索排名变化仍可查询。搜索名次不进入社会关注度排名。不要把搜索引擎返回的多个转载当作多个独立证据。

### 9. events / event_evidence / event_relations

events：稳定 UUID、工作标题、可选时间区间、状态、创建者、创建时间和版本。工作标题可以更新，事件 ID 不变化。

event_evidence：event ID、revision/observation ID、角色（initial_report/update/correction/response/impact）、关联方法、置信度（可空）、关联理由、人工确认状态、有效/撤回状态。关联改变保留审计记录。

event_relations：父子事件、后续进展、报道冲突、转载等关系，记录证据和建立方式；因果判断必须显式标为 hypothesis 或 reviewed，不能仅靠时间先后自动生成事实关系。

当前不自动生成事件簇。旧 topic ID 保存为 legacy 关联，不直接转成“已确认事件”。

### 10. analysis_records / analysis_evidence

保存分析用途、模型与 provider、prompt/schema/algorithm 版本、生成时间、输入 revision/observation/search run ID、输出 blob、状态、被哪次分析替代、token 和费用信息（未知为空）。分析追加版本；任何结论都可以回到当时的输入材料。模型输出与采集事实分开。

## 采集与写入流程

1. 在上游响应到归一化之间增加独立记录边界，先捕获并脱敏原始响应，再规范化。
2. 成功、空结果、解析失败、HTTP 失败分别落 run；直连和 fallback 分属不同 run。
3. 归一化后将文档、版本、观测、指标在一个短事务里写入。网络等待不占写事务。
4. 保留现有 `fetchSource` 返回契约与页面数据；同一套已抓到的数据进入两种用途，不重复发网络请求。
5. 旧榜单保存与证据写入遵守维护锁和 generation 检查。必须先确保证据落库，再返回“刷新已保存”；证据失败向 CLI 报告明确失败，不静默宣称完整保存。重试使用同一 run 幂等写入。
6. 初期 raw 响应可 gzip 存 SQLite BLOB，不引入新云服务；记录压缩前后字节数。后续通过 blob 仓储接口迁移对象存储。

- RSSHub：不需要 API Key，本次只作为后续 adapter 参考，不额外部署服务。

注册中的密码、验证码、身份选择和条款接受按浏览器要求交给用户；没有实际 Key 时，只提供禁用状态的配置示例，不伪造接通结果。Key 放 `.env.local` 或部署 secrets，文档和数据库只记录是否配置。

## 历史回填与兼容

- 提供独立、可重入、分批的回填 CLI，不在页面读取或应用启动时隐式扫描全库。
- 数据来自现存 raw_items 与 snapshots；每批有检查点和幂等标识，重复运行不复制历史观测。
- 标记 provenance=legacy_normalized，missing 原始响应不伪造。用 fetched_at 作 observed_at，原始发布时间没有数据则为空。
- 旧 stats 中 comments/replies 相等不能仅凭数值相等就认定重复；只有已知 adapter 映射才能记录 alias，原值仍保留。
- 在副本或临时数据库验证迁移、回填与备份恢复，然后显式执行真实库回填；本次不删除或重建原业务数据。
- 历史六表归档仍按 v1 校验和读取。回填包含归档数据需要显式参数，默认只处理在线主库；不能写入只读归档。

## 增长、备份与恢复

- 新增命令创建包含所有表的完整 SQLite 一致性备份，使用 SQLite backup API 处理 WAL；附清单、schema 版本、文件 SHA-256、表行数与 blob 总字节数。
- 备份内容不带环境变量和账户凭据；导出目录权限遵循现有私有导出目录。
- 单纯 SHA-256 用于完整性和去重，不声称证明新闻真实性或抵抗管理员修改。
- 备份恢复验证在新临时路径进行，检查 integrity_check、foreign_key_check、关键行数和压缩 blob 解码；不覆盖正在运行的数据库。
- 保留原管理员 full/daily 导出格式；在操作文案与文档中标明它们不包含新增长期资料，指向完整备份命令。先保证完整备份可用，再启用在线证据写入。
- 不执行现有业务 JSON 去重改造，不自动清理旧数据；展示新表行数、blob 压缩量和新增字节，后续再评估历史负担。
- 以后按月份归档需要做引用闭包：包含所依赖的文档版本、blob、查询和事件证据，不能仅按一张表的时间过滤。

## 验收与验证

1. 旧快照和日报可继续读取，旧归档 v1 可验证、注册和查询。
2. 两个引擎发现同一文档：一个文档、两个独立 search run/hit，查询参数和各自排名可恢复。
3. 同文档互动增加：同一正文版本、两次观测；零值与 missing 不混淆；同 run 重试不重复写入。
4. 文本更新生成新 revision；旧版本及曾引用它的分析保持可读。
5. 原始响应脱敏后可解码与校验，认证 Key、Cookie、token 不出现在库、日志和备份中。
6. 上游失败、空结果和部分分页可区分； fallback 的来源可追踪。
7. 删除临时库中的旧小时快照后，长期证据、事件和分析引用仍然存在。
8. 回填重复运行保持行数和内容一致；只使用原有数据，未采到的信息仍标记未知。
9. 维护任务发生在网络等待之后时，过期 generation 写入被阻止，已有证据不损坏。
10. 完整备份在独立临时库通过完整性和解码验证，旧业务归档不会被误称为全库备份。
11. 新增证据库、回填、搜索记录和备份命令默认不发外部请求、不新增 AI 费用；不会因没有新供应商 Key 而停掉既有无 Key 热榜采集，额度不足或失败不自动切付费。
12. 运行与变更相关的现有归档、维护和生产边界测试，以及新增证据库测试、lint 和类型检查；仅在需要确认应用集成时运行构建。
