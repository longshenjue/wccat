## 实现

- 六端点 catalog、统一客户端、SQLite 持久缓存/每日计数/账户调度/端点租约；独立版本 schema，不修改证据 v1 或六表归档。
- `TIANAPI_KEY` 即可开启六接口；四个既有平台单渠道选榜并保留原回退；两路辅助热榜明确出处，不计平台多样性或热度加成。
- 辅助材料进入既有 topic analysis 请求与引用关系。热搜页跳过文章正文和原图提取；未提供互动指标不伪造。
- status/check CLI、Northflank Runtime Secret 配置和已知边界见 `docs/tianapi.md`。

## 实施裁定（Rulings I made）

1. 用户明确要求开始并委托架构，沿用已选 SQLite 与长期证据方案直接落实设计和计划，不重复要求流程确认。代价：默认调用优先级由实现者决定，用户可通过 allowlist/开关调整。
2. 四平台 TianAPI 成功后不再并抓同平台旧榜；聚合与腾讯生态只补证据。避免重复计分，代价是辅助榜独有话题不直接入总榜，四平台可用文章链接可能少于旧直连。正文仍由其他现有文章来源补充，另抓旧榜恢复链接属于后续功能。
3. 真实账户权限、实时成功率和供应商侧计费仅能在已配置账户的环境验证。代价：本地夹具与真实 SQLite 测试不代表真实 Key 已连通；交付容器 check 命令，不虚报实测。
4. 本次新增输入只扩展话题分析；日报草稿撰写、翻译、分享图等其他生成链路未普遍注入辅助列表。代价：后续产物主要通过已有话题分析间接受益；直接调用话题分析的日报 TOP1 已在本次补齐证据链。
5. 计数、节流仅协调共享本 SQLite 的进程。代价：其他数据库/应用和控制台调用仍需自行管理总配额；默认 90 预留余量不能代替账户统一计量。

没有延期的审查问题。没有读取、写入或提交真实 Key，没有使用真实账户进行请求，没有迁移/回填用户历史数据库。
